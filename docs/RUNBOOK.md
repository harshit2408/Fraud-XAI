# Serving Runbook

Operational procedures for the fraud-detection API. Written for Phase E task
E6; the `mle-workflow` skill requires that every deployment name its rollback
artifact, config, data dependency, and traffic switch before it ships.

Companion documents: [ADR-001](adr/ADR-001-inference-orchestration.md)
(inference orchestration), [ADR-002](adr/ADR-002-realtime-feature-state.md)
(real-time feature state).

---

## 1. What is deployed

One `fraud-api` container serves a **3-model calibrated ensemble** behind a
frozen operating point.

| Artifact | Path | Notes |
|---|---|---|
| XGBoost | `models/xgb_model.pkl` (+ `.meta.joblib`, `.checksums.json`, `.manifest.json`) | 0.692 of the blend |
| LightGBM | `models/lgbm_model.txt` (+ sidecars) | 0.174 |
| TFT | `models/tft_model.weights.pt` (+ sidecars) | 0.134; sequential, needs a per-card window |
| Feature transformers | `models/transformers/` | encoders, PCA, imputer, target-encoding state, card accumulators |
| Ensemble spec | `models/ensemble.json` (+ `.checksums.json`) | weights + **per-mode thresholds** |

`model_version` = `{dataset_hash[:12]}-{config_hash[:12]}-{git_sha[:7]}`,
returned in every `/predict` response, every prediction-log line, and `/health`.

**Startup fails closed.** The registry refuses to start on a checksum
mismatch, a missing calibrator, a dataset-hash disagreement, or an ensemble
spec fitted against different models. A container that will not come up is the
intended outcome — it is strictly better than serving a mixed-vintage ensemble.

## 2. Rollback

Rollback is a **file swap plus a restart**. It never requires retraining.

```bash
# 1. Identify the currently serving version.
curl -s localhost:8000/health | jq -r .model_version

# 2. Restore the previous artifact set (all five together — see the warning).
cp -r backups/models-<previous-version>/. models/

# 3. Restart. The registry re-validates every artifact on the way up.
docker compose restart fraud-api

# 4. Confirm the version actually changed.
curl -s localhost:8000/health | jq -r .model_version
```

> **Roll back the whole set, never one model.** The blend weights and the
> threshold in `models/ensemble.json` were fitted against one specific trio of
> models. Restoring a single model beside a newer spec produces scores that are
> not wrong-looking, just wrong. The dataset-hash check catches the common case
> at startup, but it cannot catch two artifact sets that share a dataset.

**Traffic switch:** a single replica, so the restart *is* the switch (a few
seconds of 503 while the registry loads). For a zero-downtime rollout, start a
second container on the previous artifacts and move the load balancer, then
stop the old one.

**Config rollback:** `config/config.yaml` is versioned in git. `git checkout
<sha> -- config/config.yaml` then restart. Note that `config_hash` covers the
whole file, so a config-only rollback changes `model_version`.

**Data dependency:** `models/transformers/` must match the models. It is
regenerated by `python src/data/preprocess.py`, which also refreshes
`data/processed/*.parquet` — the drift reference. Never roll back models
without the transformers that were fitted alongside them.

## 3. Health and observability

`GET /health` returns liveness, `model_version`, loaded models, `known_cards`,
and an `observability` block. That block exists because each signal in it is a
way the service **keeps answering while getting worse** — none raises, none
appears as an error rate.

| Signal | Meaning | Action when it moves |
|---|---|---|
| `cards_scored_with_partial_sequence` | TFT scored on a window shorter than the trained 10 | Expected to spike after every restart (the sequence buffer is not persisted, ADR-002 §5.6) and decay as traffic refills it. **A sustained high value means the buffer is never filling** — check whether one card dominates traffic, or whether requests are being spread across replicas. |
| `out_of_order_transactions` | A transaction arrived earlier than its card's last-seen timestamp, within the staleness tolerance, and was clamped | A steady non-zero rate means the upstream is not ordered by `card1`. For Kafka, confirm the topic is partitioned by `card1` — ADR-002 §5.3 makes that a **correctness** requirement, not tuning. |
| `duplicate_transactions` | Redelivery rejected by the idempotency guard | Normal and healthy under at-least-once delivery. A sharp rise means an upstream producer is retrying — investigate there, not here. |
| `target_encoding_state_age_seconds` | Age of the target-encoding state, anchored to the artifact's mtime | Grows without bound by design: there is **no label feed** in this deployment, so the encodings are frozen (ADR-002 §5.5). Treat a large value as a prompt to re-run preprocessing, not as a fault. |
| `config_hash_mismatch` | Artifacts were trained under different `config.yaml` contents | Expected for the shipped set (LightGBM was trained after an `early_stopping_rounds` edit). **Verify the difference is confined to sections that cannot affect the earlier models** — `config_hash_detail` names the differing hashes. |

### 3.1 Prometheus metrics — `GET /metrics`

`prometheus-fastapi-instrumentator` exposes `/metrics` in Prometheus text
format. `monitoring/prometheus.yml` scrapes it every 15s; the Grafana dashboard
(`monitoring/grafana/dashboards/fraud_detection.json`) charts it.

| Metric | Type | Set by | Panel |
|---|---|---|---|
| `fraud_predictions_total{decision}` | Counter | `InferenceService.predict` (one path for HTTP + Kafka) | Fraud Rate, Request Volume |
| `http_request_duration_seconds` | Histogram | instrumentator (automatic) | Prediction Latency P95 |
| `fraud_model_version{version}` | Gauge (=1) | startup, from the loaded bundle version | Model Version |
| `fraud_drift_detected` | Gauge (0/1) | `drift_scheduler` on each run | Feature Drift Indicator |
| `fraud_consumer_lag` | Gauge | Kafka consumer, once per poll | Kafka Consumer Lag |

`fraud_consumer_lag` is the backlog in messages (sum of `highwater - position`
over assigned partitions). **`-1` means "not yet known"** — no partition
assignment, or the broker has not reported a high-water mark — and is
deliberately distinct from a genuine `0`, so an unmeasured backlog is never
charted as healthy. PRD §6.4 budgets this at **< 500** during the streaming
demo; that is the red threshold on the panel and the check
`scripts/streaming_stats.py` enforces.

`/metrics` and `/health` are excluded from the latency histogram so probe
traffic does not distort the P95.

## 4. Drift monitoring

```bash
make monitor                              # compares the last 5000 predictions
python src/monitoring/drift_reporter.py --current data/processed/test_features.parquet
```

- **Reference:** `data/processed/train_features.parquet` — what the models were
  fitted on, which is what makes "retrain" the actionable response.
- **Current:** reconstructed from `logs/predictions.jsonl`, written by
  `PredictionLogWriter` on every scored request.
- **Alert:** more than `monitoring.drift_share_threshold` (default 30%) of
  compared features drift. **Exit code 1 on drift**, so a scheduler fails
  loudly instead of needing someone to open the HTML.
- **Output:** `monitoring/reports/{name}.html` and `{name}.json`.

The reporter **raises** rather than reporting "no drift" when the window is
empty, entirely null, or shares no features with the reference. A monitoring
job that stays green while comparing nothing is the failure this guards against.

**Data drift only.** Model-performance reports need `y_true`, and confirmed
fraud labels arrive on a ~30-day lag (finding F6). There are no labels to score
at monitor time.

### 4.0 Scheduled drift checks — `make drift-scheduler`

`make monitor` is one-shot. `src/monitoring/drift_scheduler.py` is the loop
(PRD §7.4): each iteration reconstructs the window from `logs/predictions.jsonl`,
runs the reporter, and — **only when drift is detected** — writes
`monitoring/alerts/drift_alert_{timestamp}.json` and sets the
`fraud_drift_detected` Prometheus gauge. It then sleeps
`monitoring.drift_check_interval_hours` (default 24h) and repeats.

```bash
make drift-scheduler                                          # runs forever, 24h interval
python src/monitoring/drift_scheduler.py --once               # single check, exit
python src/monitoring/drift_scheduler.py \
    --max-iterations 2 --interval-seconds 300                 # bounded run (PRD done-when)
```

- A single iteration that raises is logged and the loop continues — it does not
  die on the first bad window.
- No prediction log yet → the iteration is **skipped** (logged), not an error.
- The alert file and the gauge both exist on purpose: the gauge is live state
  Grafana reads and is lost on restart; the alert file is the durable,
  diffable audit trail.
- Exit code is non-zero only for a **bounded** run that produced zero reports —
  a cron wrapper can then alert that monitoring is not seeing data.

### 4.1 SHAP explainability dashboard

```bash
conda run -n fraudx python scripts/generate_shap_dashboard.py            # 5000-row sample of the test split
conda run -n fraudx python scripts/generate_shap_dashboard.py \
    --features data/processed/val_features.parquet --sample 3000
```

- **Input:** a processed feature parquet (`data/processed/test_features.parquet`
  by default) — already engineered and column-aligned to the model, so the
  dashboard explains the exact vector the model scores.
- **Scope:** TreeSHAP over the **XGBoost component only** (0.692 of the blend,
  ADR-001 §3.4). The page states this and the weight; it is not an explanation
  of the ensemble decision.
- **Output:** one self-contained `monitoring/shap_dashboard.html` — global
  importance (mean |SHAP|), a per-transaction SHAP distribution, and a
  top-feature table, all figures inlined as base64 PNGs (no network, opens
  from `file://`).
- Run it after a retrain, or when a reviewer or regulator asks for the current
  model's global feature attribution.

### 4.1b Business impact report (PRD Phase 8)

```bash
make business-impact          # export probabilities, then execute the notebook
# or step by step:
python scripts/export_test_probabilities.py
jupyter nbconvert --to notebook --execute --inplace notebooks/05_business_impact.ipynb
```

- **Run it after a retrain or any threshold change** — the notebook quotes the
  weights and threshold from `models/ensemble.json`, so it goes stale the moment
  those move.
- **Two steps on purpose.** The export loads XGBoost, LightGBM and the TFT
  (torch) to score the test split once, and writes
  `reports/ensemble_test_probabilities.npz`. The notebook then reads only that
  file, so re-running the analysis never reloads a model.
- **Run with the docker stack DOWN.** The export needs torch on the host; while
  compose is up, importing torch fails with `WinError 1455` (paging file).
- **Arithmetic lives in `src/evaluation/business_impact.py`**, unit-tested — the
  notebook is presentation only.
- **The report shows two cost conventions side by side.** `config.yaml` credits
  `revenue_tp=480` on a catch and charges `cost_fn=500` on a miss, double-counting
  the same principal; §6 quantifies that this alone moves the optimal threshold
  2.2x. Do not quote one net-value figure without the other.

## 4.2 Real-time inference stream (Kafka)

The `fraud-api` container runs a Kafka consumer as an asyncio background task in
the **same process** as the HTTP app (PRD §6.3). It calls the identical
`InferenceService` — one scoring path, one shared feature-state store. There is
no separate consumer container.

```bash
make streaming-demo            # docker compose up, wait healthy, produce, summarize
# or step by step:
docker compose up -d
python src/streaming/producer.py --rate 200 --limit 5000    # raw test transactions → 'transactions'
python scripts/streaming_stats.py                           # summary from /health
```

- **Producer** streams RAW `data/raw/test_transaction.csv` rows (left-joined
  with `test_identity.csv`), keyed by `card1` so each card is single-writer on
  one partition (ADR-002 §5.3). It is a one-shot CLI script, never a service.
- **Consumer** polls `transactions`, scores in-process, and publishes every
  FRAUD decision to the `fraud_alerts` topic keyed by `card1`.
- **Health:** `curl -s localhost:8000/health | jq '{kafka_consumer_running,
  kafka_messages_processed, kafka_alerts_published, kafka_consumer_errors,
  kafka_consumer_lag}'`.
- **Lag budget:** `kafka_consumer_lag` (also the `fraud_consumer_lag` gauge,
  §3.1) must stay under 500 during the demo. `scripts/streaming_stats.py` exits
  non-zero if it is at or above that, and reports "not evaluated" rather than
  passing when the lag reads `-1` (unknown).
- **Broker address:** `config.kafka.bootstrap_servers` (`localhost:9092`) is
  the default; `docker-compose.yml` sets `KAFKA_BOOTSTRAP_SERVERS=kafka:9092`
  and `load_settings` overlays it when set and non-empty. So under compose the
  consumer talks to `kafka:9092` with no config edit; a local run uses
  `localhost:9092`. `config_hash` reflects whichever was used.
- **Broker down at startup:** the API still comes up serving HTTP;
  `kafka_consumer_running` is `false`. `FRAUD_API_DISABLE_KAFKA=1` skips the
  consumer entirely (HTTP-only deployments, tests).
- **Concurrency:** the consumer thread and the HTTP threadpool share one
  `InMemoryFeatureStateStore`. The read-then-write ordering, `TransactionID`
  idempotency guard, and `RLock` (Phase E) cover both writers — the consumer
  adds no new shared state.

| Symptom | Cause | Fix |
|---|---|---|
| `kafka_consumer_running: false` after startup | Broker unreachable when the lifespan ran | Check the `kafka` container; restart `fraud-api` once it is healthy |
| `kafka_consumer_errors` climbing | Poisoned messages (bad schema, un-scoreable) | One bad message is logged and skipped, never fatal; inspect the server log for the `TransactionID` |
| No alerts on `fraud_alerts` | Threshold not cleared, or the producer published nothing | `kafka_alerts_published` vs. the producer's `producer finished: N` line |
| `kafka_consumer_lag` climbing past 500 | Consumer slower than the producer rate | Lower `--rate` on the producer, or check for a slow SHAP path in the server log |
| `kafka_consumer_lag` stuck at `-1` | No partition assigned yet (idle topic), or broker metadata unavailable | Expected before the first message; if it persists, confirm the topic exists and the consumer joined the group |
| `/health` and `/metrics` both time out under a large backlog | The scoring loop is saturating the worker — see the throughput note below | Not a crash; wait for the drain, or produce at a lower rate |

**Throughput note (measured 2026-09-08).** Each streamed message runs the full
ensemble: feature engineering (including the V-feature PCA), a TFT sequence
rebuild, the 3-way blend, and SHAP. That costs roughly **250 ms**, so one
`fraud-api` worker sustains about **4 messages/sec** — far below the PRD's
200 tx/sec demo rate. Publishing 3,000 messages at once therefore builds a
multi-minute backlog, and while the loop is saturated `asyncio.to_thread` leaves
the event loop little room, so `/health` and `/metrics` scrapes time out. The
practical consequence: **the lag gauge is only observable while the API can
still answer a scrape**, which is exactly when lag is least interesting. Keep
demo volumes modest (a few hundred messages), or treat sustained throughput as
the open scaling item it is — it needs batching or multiple consumers, not a
metrics change.

## 5. Common failures

| Symptom | Likely cause | Fix |
|---|---|---|
| Container will not start; `Ensemble spec not found` | `models/ensemble.json` absent | Run `python scripts/run_ensemble_eval.py` |
| Startup raises `Checksum mismatch` | Corrupted or partially copied artifact | Restore the full artifact set; do not bypass the check |
| Startup raises `trained on different datasets` | Mixed-vintage artifacts | Restore one coherent set — this check is doing its job |
| Startup raises `no frozen calibrator` | Pre-Phase-C4 artifact | Re-train; the blend is defined over calibrated probabilities |
| `/predict` returns 422 | Schema violation, or a feature missing after transform | Full detail is in the server log, deliberately not in the response |
| `/predict` returns 409 | Transaction backdated beyond the staleness tolerance | Expected — scoring it would corrupt the card's aggregates |
| `/predict` returns 503 | Models not loaded, or a mode with no frozen threshold | Check startup logs |
| `make monitor` raises `No prediction log` | No traffic served yet | Score some requests first |
| Every card cold-starts | `models/transformers/` predates ADR-002 (no `card_agg_state`) | Re-run `python src/data/preprocess.py` |

## 6. Known gaps

Recorded rather than hidden. None blocks Phase E; each has an owner phase.

1. **The TFT sequence buffer is not persisted.** Every card scores on a short
   window after a restart until traffic refills it. Measured by
   `cards_scored_with_partial_sequence`. (ADR-002 §5.6)
2. **Target encodings are frozen.** No label feed exists in this project, so
   `target_encoding_state_age_seconds` grows without bound. The promotion
   mechanism is specified in ADR-002 §5.5 so a real feed is a plug-in.
3. **SHAP explanations cover the XGBoost component only, by design.**
   `PredictionResponse.explanation` carries TreeSHAP contributions for the
   XGBoost sub-model (0.692 of the blend), with `explained_model` / `explained_weight`
   saying so (ADR-001 §3.4 — KernelSHAP over the blend was rejected on latency).
   It is *not* an explanation of the ensemble decision. Explanation is
   best-effort: if it raises **or exceeds `explainability.timeout_ms`** (default
   50 ms — TreeSHAP on the 171-feature booster is ~140 ms and would otherwise
   dominate `/predict` latency), the score is still returned with an empty
   `explanation` and `serving_metrics.explanation_failures` increments on
   `/health`. `explain_single` also self-checks additivity on the served row
   (`base_value + Σcontributions` must reconstruct the XGBoost margin); a
   violation is treated as an explainer failure, not returned. Set
   `explainability.enabled: false` to turn it off entirely (no `shap` import,
   empty `explanation` on every response); with it `true` and no loadable
   `xgb` model, startup fails rather than serving never-explainable predictions.
4. **Single replica.** `InMemoryFeatureStateStore` holds card state in-process;
   multi-replica needs the Redis adapter ADR-002 §5.1 specifies.
5. **`logs/predictions.jsonl` has no rotation or retention policy.** Every
   scored request appends a full 171-feature vector, and `make monitor` opens
   the whole file to take the tail. Bounded in practice by this project's
   traffic, but a real deployment needs size-based rollover and a retention
   window — prediction logs are joined to delayed labels, so they outlive the
   request by months. (Raised by `ecc:code-reviewer`.)
6. **No canary or shadow traffic.** Rollout is restart-in-place. Acceptable at
   this scale; a real deployment would want the second-container flow in §2.
7. **Kafka consumer offset handling is at-least-once with auto-commit.** A
   crash mid-batch re-delivers; the `TransactionID` idempotency guard
   (ADR-002 §5.3) makes that safe for the aggregates, but the `fraud_alerts`
   topic can carry a duplicate alert. Downstream alert consumers must dedupe
   on `transaction_id`.
